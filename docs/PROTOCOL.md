# Display protocol v1

A manifest is a JSON response with `schemaVersion: 1`, `image_url` (HTTP(S), absolute or relative), a 64-character hexadecimal `sha256`, `generatedAt` (Unix milliseconds), `width`, `height`, `state`, `staleAfterSeconds` and `refreshAfterSeconds`.

Pages publishes `manifest.json` for Chinese and `en/manifest.json` for English, plus immutable `images/<sha256>.png` under the corresponding folder. Existing screen.png aliases remain compatible. The plugin validates the manifest, limits response sizes, verifies image bytes, decodes a temporary file and only then replaces the cache. A manifest/image deployment race fails safely and retries. `generatedAt` means generation, not download; plain custom PNG URLs do not claim a generation timestamp. The device keeps its own refresh schedule; refreshAfterSeconds is informational in this release.

The LAN service exposes `/api/display?lang=en|zh&page=1|2|3`, returning an image URL under `/api/image/<sha256>.png`. The manifest also echoes `page` and `pages: 3`. `/api/screen` accepts the same `lang`/`page` parameters. Invalid or missing page numbers fall back to page 1. A request with no `page` parameter at all is treated as a legacy single-page client: the manifest says `pages: 1` and the image carries no page indicator, so an older installed plugin never advertises a gesture it cannot perform. Twelve recent images are retained in server memory (three pages × two languages × two flips); after restart or eviction a client must obtain a fresh manifest. Language and page never change the configured timezone or units.

Page 1 is the existing dashboard, page 2 is slow information (date, solar term, moon phase, daylight, next few days, weekend and fixed calendar days), page 3 is a single reading sentence. Pages are generated on demand and never auto-rotated: swipe left/right or tap the screen sides to change pages, and the top edge still exits. Each page has its own persistent cache on the device. Only page 1 has a cloud Pages fallback — the cloud renderer still publishes a single image, so pages 2 and 3 use LAN plus the local cache exclusively.

A custom HTTPS manifest may not downgrade its image to HTTP. TLS verification remains enabled. The first implementation does not follow HTTP redirects; configure final URLs. Failed attempts preserve the displayed image and retry with bounded backoff.
